Example 2 · Crash-bug triage at a game studio

QA files a crash bug. Before a producer reads it, an agent has already commented with the changelist that most likely caused it, the team that owns that system and a link to the design page.

What this adds to Example 1:

  • A host needs no chat window. A webhook starts the loop. The host is whatever process runs the loop and holds the clients.
  • Jira appears twice, by two routes. The webhook that wakes the host is plain HTTP. The tools the agent reads and writes through are MCP.
  • Transports can mix in one host. Remote servers over Streamable HTTP, a local one launched as a stdio subprocess in the same container.
  • The host filters the tool list: a lock. Even if the Jira server lists tools that reassign or close issues, the host never passes them to the model, so the agent cannot call them, however it is prompted.
  • Each server has its own narrow credential. The Perforce user is read-only, so even a wrong call cannot submit a changelist.
How the webhook works

A webhook is a reverse API call: instead of the host polling Jira every minute (“any new bugs?”), Jira calls the host when the event happens. Set up once: a Jira admin registers a URL (e.g. https://triage-xyz.run.app/jira-events) and a filter (issue created, type = Crash). Then, on each matching event, Jira sends an HTTP POST with a JSON body:

{"webhookEvent": "jira:issue_created",
 "issue": {"key": "GAME-4812", "fields": {"summary": "Crash in AnimGraph..."}}}
StepWhy
1. Verify the sender (shared secret or signature)The URL is public; anyone could POST a fake bug
2. Claim the event key, atomically (INSERT … ON CONFLICT DO NOTHING, or a Firestore create)Senders retry, so the same event can arrive twice. Only the request that wins the insert runs the agent. A check-then-write lets two near-simultaneous copies both pass
3. Return 200 OK at onceThe sender waits only briefly. A slow reply looks like a failure and triggers a retry
4. Run the agent in the background (e.g. Cloud Tasks)The loop takes from 30 s to minutes: several model calls plus three MCP calls
5. Mark the event done (or failed)Status separates a duplicate (skip) from a run that crashed halfway (retry)

The key: a delivery ID if the sender provides one, else issue key + event type (GAME-4812:issue_created). Keep the record in a database, not in memory: Cloud Run runs several instances and restarts them. The name for this property is idempotency: processing an event twice has the same effect as processing it once.

Example 3 · Level designer's in-editor assistant

A designer with a level open types: “Place the lanterns from the night-market brief along the main street, then tick them off in the props sheet.” The agent reads the brief, looks at the level, proposes placements, waits for the designer's OK, places the props and adds rows to the sheet.

What this adds to Examples 1 and 2:

  • The server is an adapter, not the engine. The editor does not speak MCP. The server turns each tools/call into a command for an editor plugin, sent over a local socket.
  • stdio puts the server on the designer's machine. The host starts it as a subprocess, so the MCP leg opens no network port and needs no auth. The plugin's socket is a port, though: bind it to localhost.
  • Writes change a live level, so the host asks first. The host shows each spawn_actor to the designer for approval and runs read-only calls without asking. Annotations such as readOnlyHint and destructiveHint can drive that split, but they come from the server, so rely on them only if you trust the server.
  • OAuth as the designer, not a bot. The agent can open only what the designer can, and edits are logged under the designer's name. It can also do anything the designer can, so request the narrowest scopes (read-only for Docs).
  • Plan for undo. If the plugin wraps each edit in an editor transaction, Ctrl+Z reverts the agent's change like a manual edit.

The two tool messages

MethodCarriesFilled by
tools/list → resultname, description, inputSchema (+ optional title, outputSchema, annotations)Server (from tools.yaml)
tools/call → paramsname, argumentsThe model (“model-controlled”)
tools/call → resultcontent[], isErrorServer

The round trip: client lists → host gives schemas to the model → model emits a call → client sends tools/call → server runs it → host appends the result and calls the model again.

Errors

Protocol (unknown tool, malformed)JSON-RPC error, e.g. -32602
Execution (API, validation, business rule)result with "isError": true; shown to the model

Annotations are untrusted unless the server is trusted. tools spec

Toolbox tools.yaml (current flat format)

kind: source            # one YAML document per resource, separated by ---
name: my-pg-source
type: postgres
host: 127.0.0.1
port: 5432
database: toolbox_db
user: toolbox_user
password: ${PASSWORD}   # env var substitution
---
kind: tool
name: search-hotels-by-name
type: postgres-sql
source: my-pg-source
description: Search for hotels based on name.      # → model sees
parameters:                                         # → inputSchema
  - name: name
    type: string
    description: The name of the hotel.
statement: SELECT * FROM hotels WHERE name ILIKE '%' || $1 || '%';   # never leaves the server
---
kind: toolset
name: my_first_toolset
tools:
  - search-hotels-by-name

$1, $2… = parameters in order. Parameters default to required: true. README · postgres-sql

Enforced vs. stated

A rule is enforced where it holds even if the model is tricked or wrong (a lock), and only stated where it relies on the model obeying (a sign). Test: if the model misbehaved, would the rule still hold here?

RuleSignLock
Action type in the enum (M-7)Parameter descriptionCHECK constraint
Orders never mutated (M-6)PromptNo mutating tool + only GRANT SELECT
Only your own orders (M-4, M-5)“Only this user” in the promptWHERE … AND customer_email = $2 with the email bound by the host

Bound parameters: identity from the host, not the model

ToolboxClient → load_tool("get-order-status",
                          bound_params={"customer_email": session_email})   # value or callable

The host (which ran the login) supplies the value. The docs say bound values are “not requested or modified by the LLM”. Still to check: print the loaded tool's schema and confirm the bound parameter is missing from it. toolbox-core docs

Run and load

npx @toolbox-sdk/server --config tools.yaml     # MCP at http://127.0.0.1:5000/mcp
                                               # one toolset: /mcp/<toolset_name>
from toolbox_core import ToolboxClient
async with ToolboxClient("http://127.0.0.1:5000") as toolbox:   # speaks MCP by default
    tool  = await toolbox.load_tool("get_weather")
    tools = await toolbox.load_toolset("toolset_name")
    result = await tool(location="London")

toolbox-core docs (v1.4.0). --enable-api adds /api/tool/<name>/invoke (verified, v1.16.0). Lock it to local callers with --allowed-hosts 127.0.0.1,localhost.
