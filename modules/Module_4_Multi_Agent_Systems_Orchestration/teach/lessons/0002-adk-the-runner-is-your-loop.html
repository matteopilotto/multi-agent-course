0 · From memory first

Two questions from lesson 0001. Answer them out loud before you open them.

In your build, which process is the MCP host, which is the client, and which is the server?

Host: the process running your pipeline and the ADK agent. Client: toolbox-core's ToolboxClient inside it. Server: Toolbox on :5050. Postgres is behind the server and never speaks MCP.

By default, who fills in a tool call's arguments? So what did you decide about the email?

The model fills them in, from the schema. You decided the email must not be one of them: the host binds it from the login, and the model never sees it (your learning record 0004). This lesson checks that it actually happens.

Your recorded weak spot is “who acts vs. who decides”, so read the table that way. The model decides which tool to call. The Runner acts: it calls the model, runs the tool, saves the result in the session and calls the model again. The LlmAgent doesn't do anything by itself. It's a description that the Runner reads.

2 · The four pieces in code

A toy agent, not your shop. The tool is a plain Python function:

from google.adk.agents import LlmAgent
from google.adk.runners import Runner
from google.adk.sessions import InMemorySessionService
from google.genai import types

def get_capital_city(country: str) -> str:
    """Retrieves the capital city for a given country."""
    return {"france": "Paris"}.get(country.lower(), "unknown")

agent = LlmAgent(name="capital_agent", model="gemini-2.5-flash",
                 instruction="Answer questions about capitals. Use the tool.",
                 tools=[get_capital_city])            # definition

sessions = InMemorySessionService()
runner = Runner(app_name="demo", agent=agent, session_service=sessions)

async def main():
    s = await sessions.create_session(app_name="demo", user_id="alice")
    msg = types.Content(role="user", parts=[types.Part(text="Capital of France?")])
    async for event in runner.run_async(user_id="alice", session_id=s.id, new_message=msg):
        ...                                          # section 3

The function and its docstring are the example on ADK: LlmAgent. Signatures were checked against the installed google-adk 2.13.0; create_session is a coroutine, so it needs await.

Three things to notice:

  • The function is the tool. ADK reads its signature and docstring and builds the schema the model sees. A parameter with a type hint and no default value is required.
  • A session is one conversation thread, keyed by user_id + session_id. In memory, it's gone when the process stops. If you call run_async on a session that doesn't exist, you get an error, not a new session.
  • You never call Gemini yourself. You hand the Runner a message and read what comes out.

“When you assign a function to an agent's tools list, the framework automatically wraps it as a FunctionTool.” ADK: Function tools. “A Session represents a single conversation thread” and in-memory storage keeps “None. All conversation data is lost if the application restarts.” ADK: Session

Fail loud, again

In 2.13.0, is_final_response() is also true for an error event (one with error_code set). If you print “the final text” without checking for that first, a failed turn looks like a normal answer, maybe an empty one. That's SPEC R-4 at the event level. (Read in the installed source of Event.is_final_response.)

4 · How the email disappears

Your agent's tools aren't Python functions you wrote. toolbox-core builds them from tools.yaml. The chain from config to model:

tools.yaml  →  load_toolset(bound_params=…)  →  a Python callable  →  ADK FunctionTool  →  schema sent to Gemini
 (server)        (client, inside your host)      (signature + doc)    (reads signature)     (what the model sees)

A bound parameter is removed at the third step: toolbox-core takes it out of the callable's signature and docstring and adds the value itself on every tools/call. ADK never learns it existed.

ADK's own Toolbox page: bound values “are hidden from the model.” ADK: MCP Toolbox for Databases. That page uses a ToolboxToolset from the toolbox-adk package; your env has toolbox-core 1.4.0, whose callables ADK wraps directly. Same idea, one layer fewer.

Your win: look at what Gemini sees (~5 min)

With ./run.sh toolbox running, save this outside the repo (e.g. /tmp/peek.py) and run it in the customer-support env:

import asyncio
from toolbox_core import ToolboxClient
from google.adk.tools import FunctionTool

async def main():
    async with ToolboxClient("http://127.0.0.1:5050") as client:
        tools = await client.load_toolset(
            "support-agent",
            bound_params={"customer_email": "alice.jones@example.com"})
        for tool in tools:
            decl = FunctionTool(tool)._get_declaration()   # private: a peek, not app code
            props = (decl.parameters_json_schema or {}).get("properties", {})
            print(decl.name, "->", list(props))

asyncio.run(main())

5 · Retrieval check

From memory. Your first click is the one that counts.

In ADK, which object plays the part of your Module 1 while True: loop?

The Runner calls the model, runs the tools, saves events to the session and loops. The LlmAgent is only the description it reads, and the model only decides.

Alice and Bob are both logged in. How many sessions does Stage 3 ask for?

A session is one conversation thread, so each user gets one, created at login. A shared one would put Alice's turns into Bob's context.

An event's get_function_calls() is not empty. What is happening?

A function call is the model's request. The tool's output arrives later, in a separate event that has get_function_responses() set.

A tool has a customer_email parameter, and you bind it. Where does the value go?

toolbox-core drops it from the signature that ADK reads, and adds the value to each tools/call itself. The model can't fill in a field it never sees.

Toolbox returns {"result": "[]"} for order 5. In Python, if data["result"]: evaluates to…

You saw this in Stage 2. "[]" is a two-character string, not a list. Decode it with json.loads first. Stage 4 has you unwrap it before emitting tool_result.

is_final_response() is true. Is it safe to print the text as the answer?

An event with error_code set also counts as final. Check for it, and turn it into an error event (SPEC §7.1) rather than a reply.
