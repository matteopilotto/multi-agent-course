MCP: what crosses the wire

Before you write tools.yaml, know exactly what the model sees, and what it gets to fill in.

The one win

By the end of this lesson you can name the three MCP roles in your own build, write the two messages that matter from memory, and answer Stage 2's design question with a reason.

1 · Where MCP sits in your build

Assignment 3 uses all three protocols. In one line each: ADK defines the agents, A2A connects agents running as separate services, and MCP feeds an agent its tools. This lesson covers only the blue arrow.

2 · Three roles, one per box

Definitions quoted from the official MCP architecture overview. It also says the host creates “one MCP client for each MCP server.”

RoleThe spec's definitionIn your build
Host“The AI application that coordinates and manages one or multiple MCP clients”The process running your pipeline and the ADK agent
Client“A component that maintains a connection to an MCP server and obtains context from an MCP server for the MCP host to use”toolbox-core's ToolboxClient, inside that process
Server“A program that provides context to MCP clients”The Toolbox process on :5000, configured by tools.yaml

Every message between client and server is JSON-RPC 2.0, carried over either stdio (local subprocess) or Streamable HTTP (POST, optionally streamed back with SSE). Your build uses HTTP.

3 · The two messages that matter

MCP servers can also expose resources and prompts, but your agent only needs tools. For tools, two methods do almost all the work.

tools/list: what the model gets to see

Trimmed from the spec's own example in Tools (revision 2026-07-28). The spec leaves out the _meta field that every request carries; this lesson does too.

// result of tools/list (one tool shown)
{ "name": "get_weather",
  "description": "Get current weather information for a location",
  "inputSchema": {
    "type": "object",
    "properties": {
      "location": { "type": "string", "description": "City name or zip code" }
    },
    "required": ["location"] } }

tools/call: what the model gets to fill in

{ "jsonrpc": "2.0", "id": 2, "method": "tools/call",
  "params": { "name": "get_weather",
              "arguments": { "location": "New York" } } }

Who chooses that arguments object? The spec puts it plainly: tools are “model-controlled, meaning that the language model can discover and invoke tools automatically based on its contextual understanding and the user's prompts.”

This is the harness you built in Module 1, with one change: the tool list now comes from a server instead of your TOOLS dict. One full round:

  1. The client sends tools/list; the server answers with names, descriptions and schemas.
  2. The host passes those schemas to the model along with the conversation.
  3. The model answers with a tool call: a name and an arguments object it generated.
  4. The client sends that as tools/call; the server runs the tool and returns content.
  5. The host appends the result and calls the model again.

This is your recorded weak spot, “who acts vs. who decides”. Each step has exactly one actor. Say it out loud.

4 · From tools.yaml to inputSchema

Toolbox builds those schemas from tools.yaml. Here is the example from the Toolbox README, a hotel database, deliberately not your shop:

kind: source
name: my-pg-source
type: postgres
host: 127.0.0.1
port: 5432
database: toolbox_db
user: toolbox_user
password: my-password
---
kind: tool
name: search-hotels-by-name
type: postgres-sql
source: my-pg-source
description: Search for hotels based on name.
parameters:
  - name: name
    type: string
    description: The name of the hotel.
statement: SELECT * FROM hotels WHERE name ILIKE '%' || $1 || '%';

postgres-sql docs: “$1 will be the first parameter specified, $2 will be the second parameter, and so on.”

Read it as a mapping: name and description pass through, and parameters becomes the inputSchema. $1 is filled from the first parameter. And the statement? Hold that thought.

Try it: predict, then reveal

Without scrolling up, write the tools/list entry the model would get for search-hotels-by-name. Then answer: does the SQL statement ever reach the model?

Reveal 
{ "name": "search-hotels-by-name",
  "description": "Search for hotels based on name.",
  "inputSchema": { "type": "object",
    "properties": { "name": { "type": "string", "description": "The name of the hotel." } },
    "required": ["name"] } }

No. The statement and the source (including the password) stay on the server. The model sees the contract, never the implementation. Toolbox may add fields of its own; you'll see the real output in Stage 2. (required because Toolbox parameters default to required: true.)

Source drift: check before Stage 2

The current Toolbox docs use this flat format: one YAML document per resource, each with a kind:, separated by ---. Older tutorials use top-level sources: / tools: maps. Checked against Toolbox 1.16.0 (--help): --enable-api does exist and adds the /api/tool/<name>/invoke route that TECHNICAL.md's checks use; MCP itself is at /mcp. Default port is 5000, which macOS AirPlay Receiver holds, so this build uses 5050. When in doubt, --help wins over any doc.

5 · When a tool fails

MCP has two kinds of failure, and they travel differently (spec, Error Handling):

  • Protocol error (unknown tool, malformed request): a JSON-RPC error, e.g. code -32602.
  • Execution error (API failure, bad input, business rule): a normal result with "isError": true, which the client should show to the model so it can correct itself.

Keep this in mind for Stage 4: a failure that comes back looking like a normal result is easy to miss. That's why the assignment says fail loud (SPEC R-4).

Also remember that the tool's result is the model's fourth view of a tool, after name, description and schema. Anything a tool returns, including a raw exception message that contains a request URL with an API key in it, goes into the model's context, the reply, and the trace. Return short errors you wrote yourself.

6 · Retrieval check

From memory. Your first click is the one that counts.

In your Assignment 3 build, which process is the MCP server?

The server is the program that serves tools to clients: Toolbox, configured by tools.yaml. Postgres sits behind it and never speaks MCP. The ADK agent's process is the host, and toolbox-core inside it is the client.

What does the model actually see about a tool before calling it?

tools/list returns name, description and inputSchema (plus optional fields like title and annotations). The statement and the connection details never leave the server.

What goes in the params of a tools/call request?

{"name": ..., "arguments": {...}}. That's all. The server knows nothing about your session unless something puts it into those arguments.

By default, who decides the values inside arguments?

Tools are “model-controlled”: the model reads the inputSchema and generates the arguments. Keep this one in mind for the next section.

A tool's database query times out. How should a server that follows the spec report it?

An execution failure is a result with isError: true, so the model can see it and react. JSON-RPC errors are for protocol problems such as an unknown tool name.
